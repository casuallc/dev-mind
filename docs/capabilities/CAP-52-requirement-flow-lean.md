# CAP-52 需求流程精简：一次点击的规划会话与需求级开发会话

> 能力 ID：CAP-52 ｜ 分类：流程层 ｜ 状态：**需求定稿待评审** ｜ 日期：2026-09-21
> 取代 CAP-14 FR-01~FR-05（阶段动作与会话分流）、CAP-38 FR-03（自动拆分/自动固化/自动派发）、
> CAP-37 FR-03（阶段上下文串联）；保留 CAP-38 FR-01/FR-02（跳过标记与阶段 Tab，语义降级为
> 只读展示 + 产出范围）、FR-04~FR-06。
> 依赖 CAP-51：需求粒度工作区（同需求一树一分支、需求内串行共用）正是「一个需求一个开发会话」的前提。

## 1. 目的

现有链路把「需求 → 可执行代码」拆成 4 个人工/自动接力的阶段，每阶段一个独立 claude 进程，
进程之间只靠字符串拼接传上文。实测成本结构（一个需求，N = 工作单元数、无上限）：

| 环节 | 现状 | 代价 |
|------|------|------|
| 会话数 | 分析 → 方案 → 拆分 → N 个执行 = **3 + N 个 claude 进程** | 每个进程至少 1 次 LLM 请求，外加进程内每轮工具调用 |
| 人工点击 | 「开始分析」「生成方案」两次（拆分/派发已自动） | 三步里两步要人盯 |
| 上下文注入 | **每个会话**按 sessionId 重新装配：项目知识库全量 active 条目 + 项目私有 skills + 需求附件，无跨会话复用 | 同一批知识被注入 3 + N 遍（token 与请求双付） |
| 上文传递 | 方案全文（**不截断**）塞进拆分 spec，分析截断 4000 字符；拆分产出再逐条写进 WI.spec | 长文本反复进上下文 |
| 拆分粒度 | prompt 只有一句「拆分为可独立派发执行的工作单元」，**无条数上限、无最小粒度约束**，validator 也不校验条数 | 模型倾向拆细 → N 变大 → 请求数线性涨 |

本能力做三件事，把上表每一项都压掉一个数量级：

1. **前置三阶段合并为一个规划会话**（分析 + 方案 + 拆分同一条对话上下文，产出三个文件）
   —— 会话数 3 + N → **2**，上下文重复注入 3 + N 遍 → **2 遍**；
2. **开发阶段需求级一次做完**（一个需求一个开发会话，按工作单元清单顺序改代码）
   —— 配合 CAP-51 的需求工作树，同需求内改动天然累积在一条分支上；
3. **上下文分层注入**（知识/技能/附件只在规划会话注入一次，执行会话只带工作单元 spec）
   —— 规划结论落到工作单元 spec 里，执行会话不再重复读同一批知识。

一句话心智：**一个需求 = 一次点击 → 一个规划会话（产出分析/方案/工作单元）→ 一个开发会话（改到能验收）**。

## 2. 功能需求

### FR-01 三合一规划会话

- 新增流程动作「开启 AI 规划」：`POST /api/projects/{pid}/requirements/{rid}/flow/plan`，
  起**一个**挂需求（`requirementId`，无 `workItemId`）的会话，taskSpec 首行标记 `[flow:plan]`。
- taskSpec 一次性给全：需求内容 + 附件（CAP-40 注入）+ 输出契约（三个文件、各自格式要求）。
  **不再**分三次注入上游产出——三个产出在同一条对话里产生，上文天然共享，服务端不需要拼字符串。
- 产出契约（`FlowOutputContract`）：

  | 文件 | 内容 | 缺失时 |
  |------|------|--------|
  | `.devmind/output/analysis.md` | 影响面 / 复杂度 / 风险点 | 跳过分析登记，发 P1 |
  | `.devmind/output/design.md` | 总体思路 / 模块与数据模型 / 接口 / 测试要点 | 跳过方案登记，发 P1 |
  | `.devmind/output/wi-plan.json` | 工作单元清单（FR-03 约束） | **不固化 WI**，发 P1 引导手工建 |

- **产出范围可收窄**：`analysis_skipped` / `design_skipped` 两个存量标记降级为「规划会话的产出范围」
  （跳过分析 → 只要 design.md + wi-plan.json），**不再是阶段门禁**——只有一个动作，没有下游要解锁。
- 重复触发：同需求已有进行中会话 → 409（复用服务端「同需求互斥」预检）。

### FR-02 产出登记（三个文件独立 best-effort）

规划会话 `session.completed(success)` 后，按 `[flow:plan]` 分流，逐文件登记，**单文件失败不拖垮其余**：

- `analysis.md` → 分析文档（kind=analysis，已有文档走 `saveVersion` 版本化更新）+ ANALYSIS 产物登记；
- `design.md` → 方案文档（kind=design）+ `Design(DRAFT)` + DOC 产物登记；
- `wi-plan.json` → 校验后固化 WI（建 `depends_on` 边，见 FR-03/FR-04）。

三者都成功才发一条 P1 `flow.plan.done`（「分析/方案/工作单元已就绪，开发会话已启动」）；
有缺失发 `flow.plan.partial`，正文列出缺哪个文件与后果。**删除** `flow.analysis.*` /
`flow.design.*` / `flow.split.*` 三条通知类型的产生点（存量通知历史保留）。

### FR-03 工作单元粒度约束

拆分从「辅助快速创建工作单元」变成「开发会话的工作清单」，粒度必须与「一个会话做完」匹配：

- **prompt 硬约束**（写进 `planSpec`）：产出 **1~3 个**工作单元；一个工作单元 = **一次可独立验收的
  改动**（一个功能点 / 一处缺陷 / 一次改造）；**禁止**按文件、按接口、按方法、按「写测试 vs 写实现」
  拆分；`dependsOn` 仅在有真实先后依赖时使用。
- **`spec` 必须自包含**：执行会话看不到知识库与需求附件（FR-05），所以 spec 要写清改哪些文件/模块、
  遵循的项目约定、验收标准（怎么跑、看什么）。这条是 FR-05 成立的前提，prompt 与 validator 双重强调。
- **validator 加上限**：条数 > 5 → 校验失败，走 `flow.plan.partial` 降级通知人工（不静默截断、
  不自动固化），人可在工作单元 Tab 手工建或重新规划。条数 1~5 视为可接受（prompt 目标 1~3 是软目标，
  硬上限只是护栏）。
- `title` 一句话、`type` 缺省 DEVELOPMENT 等既有解析口径不变。

### FR-04 需求级开发会话

- 固化 WI 后**不再逐 WI 派发**，起**一个**需求级会话：`[flow:dev]` + 挂 `requirementId`
  （**不挂 `workItemId`**，避免复用 WI 会话的「一 WI 一会话」语义），taskSpec = 工作单元清单
  （编号 / 标题 / spec 全文 / 依赖顺序）+ 收尾要求（全部做完整理改动、写清完成情况）。
- 清单顺序 = 固化顺序（即规划会话给出的原序，模型声明 `dependsOn` 时已自排先后），
  依赖关系在 spec 里以「先完成 #1 再做 #3」显式写出，同时固化进 `relations` 供人查看。
- 工作区：`[flow:dev]` 与 `[flow:plan]` 同挂需求 → CAP-51 同一个 `workspaceKey = req-<id>`
  → 同一棵工作树、同一条 `feature/req-<id>` 分支（规划会话只写平台排除路径 `.devmind/output/`，
  不污染工作树）。
- 不挂 `workItemId` 还有一处硬约束：CAP-38 FR-05 对「挂需求、无 WI、taskSpec 非 `[flow:` 开头」的
  新会话会自动建 DEVELOPMENT 型 WI 并把会话挂上去——`[flow:dev]` 带流程标记，天然不进这条路径；
  若实现时误挂 `workItemId`，WI 固化计数与会话归属都会被这条规则二次污染。
- **`WorkItemOrchestrator` 的自动派发停用**：`flow.split.confirmed` 事件保留（供通知/深链），
  但编排器不再据此起会话；`workitem.status.changed` → `dispatchReady` 的链路整体下线
  （**否则一次固化会掀起 N 个执行会话，正是本能力要消灭的**）。人工在工作单元行内「起会话」
  保留为逃生门（对单个 WI 单独重跑），`startWorkItemSession` 端点不动。
- 开发会话失败：WI 保持 IN_PROGRESS，走统一监听器 P0 + 通知；人可重新起开发会话
  （`POST .../flow/dev` 显式重起，或直接在工作单元行内起会话）。

### FR-05 上下文注入分层

| 会话类型 | 知识库条目 | 项目 skills | 需求附件 | 权限白名单 |
|----------|-----------|-------------|----------|-----------|
| 规划会话（`[flow:plan]`，挂需求） | 全量（现状口径） | 全量 | 注入 | 注入 |
| 开发/工作单元会话（**有 `workItemId`**，含 `[flow:dev]`） | **不注入** | **不注入** | **不注入** | **照常注入** |
| 手工会话（无 `workItemId`、无流程标记）/ chat | 现状口径不变 | 现状口径不变 | 现状口径不变 | 注入 |

- 实现口径：执行类会话的装配请求 `projectAuto=false` 且不传 `requirementId`（附件 provider 无输入即
  零产出）——**不新增装配字段**，既有开关即可表达。判定依据是「会话是否挂工作单元」，
  与 taskSpec 标记无关（人工行内起的 WI 会话同样走瘦上下文，语义一致）。
- **权限白名单不是「上下文注入」**：`settings.local.json`（Bash/Edit/Write 白名单）**必须照常下发**，
  否则 headless claude 在权限提示上卡死。装配管线现状是「无任何产出节 → 返回 null 不带包」，
  而白名单由知识 provider 无条件产出 → **瘦上下文下白名单会被空产出判定丢掉**，
  故须修 `ContextAssembler.assemble` 的空产出条件：`settings != null` 时**必须出包**
  （包内只有 settings、无 `CLAUDE.local.md` 内容节）。
- 代价与逃生门：知识不再随执行会话注入，agent 只能靠 spec 里的信息——这正是 FR-03 要求 spec 自包含的
  原因。需要边走边查知识时，用不挂 WI 的手工会话（全量注入）做，改完再回到需求流程。

### FR-06 状态流转与验收

```
DRAFT ──开启 AI 规划──> ANALYZING ──规划产出固化 WI──> IN_PROGRESS ──开发会话成功──> ACCEPTANCE ──人工验收──> DONE
```

- 规划会话创建成功：DRAFT → ANALYZING（与现状 `startAnalysis` 同口径）。
- WI 固化成功：→ IN_PROGRESS。
- 开发会话成功：→ ACCEPTANCE，发 P1 `flow.dev.done`「开发会话已完成，请验收」；
  **不自动置 WI 为 DONE**——CAP-17 执行链按 WI DONE 触发构建，N 个 WI 一起自动 DONE 会掀起 N 次构建，
  且违背「AI 产出、人验收」的既有原则。工作单元 Tab 提供「全部完成」批量翻转（逐条走既有
  `updateStatus`，构建触发语义不变），或逐条确认。
- `DESIGNING` 状态在本流程中**不再进入**（不再创建 DESIGN 型 WI）；存量处于 DESIGNING 的需求照常显示。
- 收口（CAP-51 的「收口合并到基线」）**仍为人工动作**，保留在需求详情页：开发会话成功不代表改动可进基线。

### FR-07 入口收敛

- 前端需求详情页顶部改为**一个主按钮**「开启 AI 规划」（终态/有进行中会话时禁用并说明原因）；
  规划完成后按钮变「重新规划」+ 出现「重新开发」。
- 阶段 Tab（需求分析 / 方案设计 / 工作单元）**保留为只读展示**：Tab 顺序不变，展示产出与状态，
  删除「开始分析」「生成方案」「AI 拆分」「跳过分析」「跳过方案」按钮。
- 存量端点 `flow/analyze`、`flow/design`、`flow/split`、`flow/skip` 在**前端切换完成后删除**
  （同一发行版内切换，`devmind-open-api` 未暴露这些路径，无外部调用方；`tests/` 下 E2E 脚本同步改）。
- 新增：`POST .../flow/plan`（起规划）、`POST .../flow/dev`（弃用后重起开发会话）。

## 3. 门禁矩阵

| 动作 | 条件 | 不满足 |
|------|------|--------|
| 开启/重新规划 | 需求非 DONE/CANCELLED 且无进行中会话 | 409 |
| 固化为 WI | 清单非空、通过校验（含条数 ≤ 5） | 不固化，P1 `flow.plan.partial` |
| 起开发会话 | 规划成功固化 WI 且无进行中会话 | 不自动起，P1 引导手工 |
| 重新开发 | 需求 IN_PROGRESS/ACCEPTANCE 且无进行中会话 | 409 |
| 人工行内起会话 | WI 非终态且有 spec | 409（现状不变） |

## 4. 非目标

- 不改 CAP-17 执行链（WI DONE → 构建 → 部署 TEST）的触发与幂等语义。
- 不自动收口、不自动推基线：开发会话成功 ≠ 改动可进主干，收口仍由人点。
- 不删 `WorkItemOrchestrator` 与 `DispatchPlanner` 代码：编排器只停用两条自动派发触发路径
  （`flow.split.confirmed`、`workitem.status.changed`），类与 `dispatchReady` 方法保留（可被人工
  或后续「按 WI 分派」重新接上），避免一次能力精简顺带删除别的东西。
- 不动 chat / worklog / 构建会话的注入口径。
- 不做历史数据迁移：存量需求的重跑走同一入口（重新规划会用新模板重产三份文件）。

## 5. 验收标准

1. 新需求点一次「开启 AI 规划」→ **只起 1 个** `[flow:plan]` 会话；预写三个产出文件后，
   分析文档、方案文档、N（1~5）个工作单元**一次全部就绪**，并发出一条 `flow.plan.done`。
2. 规划产出缺 `wi-plan.json` → 不固化 WI、不静默成功，发 `flow.plan.partial` 说明缺什么。
3. 规划产出 6 条工作单元 → 校验失败、不固化、发 `flow.plan.partial`（不截断成 5 条）。
4. 固化后**只起 1 个** `[flow:dev]` 会话，不再逐 WI 派发；工作单元全部转 IN_PROGRESS。
5. `[flow:plan]` 与 `[flow:dev]` 的 launch 帧带**同一个** `workspaceKey = req-<id>`（CAP-51），
   两次会话落在同一棵工作树与同一条分支；开发会话提交后工作树可见。
6. 上下文包：规划会话含知识/技能/附件；`[flow:dev]` 与人工 WI 会话**不含**知识条目与附件，
   但**必须含** `settings.local.json` 权限白名单（瘦上下文下也不得丢包）。
7. 开发会话成功 → 需求 ACCEPTANCE + P1 通知；工作单元仍为 IN_PROGRESS（未自动 DONE），
   人点「全部完成」后逐条 DONE 并照常触发 CAP-17 构建。
8. chat / worklog / 手工会话 / 构建链路的注入与派发零回归；`mvn -q test` 全绿。
9. 存量需求：处于 DESIGNING/DONE 的照常显示；已有跳过标记的需求重新规划时按标记收窄产出范围。

## 6. 分期

- **M1 后端**：`planSpec`/`planDevSpec` 模板 + `[flow:plan]`/`[flow:dev]` 分流 + 三文件登记 +
  粒度 validator 上限 + WI 固化后起需求级开发会话 + 编排器派发停用 + 注入分层（含 `ContextAssembler`
  空产出条件修正）+ 端点 `flow/plan`、`flow/dev` + 单测。
- **M2 前端与入口收敛**：需求详情页单按钮 + 三 Tab 只读化 + 工作单元「全部完成」批量翻转 +
  删除 `flow/analyze`/`flow/design`/`flow/split`/`flow/skip` 端点与旧 UI + E2E 脚本同步。
- **M3 观测与调优（可选）**：按需求统计会话数/请求数/token（会话表已有 usage 字段则直接聚合），
  用于校准工作单元粒度上限与「是否值得再合并开发会话与收口」。
