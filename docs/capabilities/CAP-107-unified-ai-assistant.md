# CAP-107 统一 AI 助手与受控能力接入

> 能力 ID：CAP-107 ｜ 分类：组装层 ｜ 状态：定稿未实施 ｜ 日期：2026-11-03
> 依赖：CAP-76（工具网关、确认单、计划、审计）、CAP-108（核心授权底座）、CAP-01/102/103（身份、角色与操作权限）、CAP-62（资源权限）、CAP-67（用量）、CAP-105（需求草稿）；外部接入复用 CAP-20。
> 决策记录：
> 1. **统一会话入口，复用已有网关**：在 Web 全局提供助手，复用 CAP-76，不另建工具循环、确认单或计划引擎；一个入口可管理多段会话，不把所有项目与任务塞入永久单会话。
> 2. **以受控工具为边界，不以 HTTP 为唯一边界**：内置助手由工具执行器调用应用 Service；独立部署或外部助手通过 Open API 接入同一应用 Service。助手不得直接访问业务数据库、Repository、任意 HTTP 或未注册服务方法。
> 3. **授权在业务执行边界收敛**：页面、内置工具、Open API 使用相同业务操作标识和核心授权规则，复用现有角色与授权表。工具可见性、页面隐藏、HTTP 过滤器和用户确认均不能替代最终授权。
> 4. **短对话写必确认**：所有有业务副作用的工具先生成参数明确的确认单；只有发起人确认后才执行，执行时重新验权。纯草稿生成不等于创建业务对象，但仍检查数据读取权限及模型费用边界。
> 5. **能力扩展复用契约**：已有受控应用能力可通过注册工具元数据与执行适配器接入；新增业务逻辑、特殊结果卡片和可靠性能力仍需实现，不承诺“增加任意 API 描述即可安全上线”。
> 6. 本文修订原“助手只通过 Open API 完成任务”的初步要求；所有新增类型、字段和端点均为目标设计，不代表已实现。[CAP-108 核心授权收敛](CAP-108-core-authorization.md)独立承担授权底座与全站迁移，本 CAP 消费该能力并联合验收首批场景。

## 1. 目的

平台已有创建需求时 AI 扩充、AI 创建工作单元、AI 规划等能力，但入口、提示方式、上下文和结果展示分散。用户需要记住功能位置及各自边界，难以形成统一使用方式。

提供一个全局 AI 助手，让用户通过自然语言查询、生成草稿和发起平台操作。平台负责确定身份、校验权限与参数、征求确认、执行和记录结果；模型负责理解诉求、提出工具调用与解释结果。

统一的是 AI 交互与受控执行契约。普通人工表单与业务页面继续提供确定性操作；过渡期的原 AI 按钮逐步改为打开同一助手并预填意图与对象上下文。

本能力不包含“交代一次后长期自主推进到目标完成”。持续任务、有限委托与验收分别遵循 CAP-96/97，不因本次入口统一而放开原短对话的写确认规则。

## 2. 功能需求

### M1 全局入口、授权底座与首批闭环

- **FR-01 全局入口**：提供跨路由保留状态的侧边会话框，可收起、恢复、新建及切换会话；退出登录清理当前客户端状态。会话及事件接口必须校验属主，不能仅凭会话 ID 读取。
- **FR-02 统一能力接入**：所有助手业务操作使用注册工具。内置工具调用已纳入核心授权的应用 Service；外部助手使用受控 Open API。工具层不下探业务 Repository，业务服务内部正常持久化不受此限制；助手会话、确认单和审计仍可由各自平台模块持久化。
- **FR-03 能力清单**：按“业务操作 → 应用 Service → 工具 → HTTP/Open API”建立清单，登记权限、资源范围、风险、参数/结果 schema、幂等与异步语义、所属模块。区分已有能力、已有工具、已有公开端点和待补齐项，不以 OpenAPI 描述文档代替可调用端点。
- **FR-04 当前用户身份**：Web 取服务端认证用户，机器人沿用可信个人映射；不得接受模型或请求参数指定 actor、基础角色、roleCode、owner 或授权结论。每次执行读取当前有效账号、角色与授权，停用、删除、权限撤销立即阻断后续动作；缺失上下文不得回退 local/ADMIN。
- **FR-05 同一核心授权**：同一主体对同一业务操作与资源，在人工接口、工具和已接入的 Open API 中得到相同业务权限结论。检查基础角色、现有 ACTION 授权、项目可见性/成员关系及个人数据归属；凭证 scope 和 AI 确认仅能额外收紧。必需授权实现缺失时不开放对应能力。
- **FR-06 工具化调用**：复用工具 schema 校验、模型循环及调用预算。模型可先查项目、列需求、读取详情再提出创建；对象不明确先查询或澄清，禁止猜测 ID。首批覆盖项目/需求查询、需求草稿、创建需求、创建工作单元。
- **FR-07 写入确认**：复用 `copilot_actions`；展示目标项目/对象、完整业务参数或可完整展开的差异、后续影响和预计费用类型。用户可以修改草稿或取消；修改后产生新的参数快照，原确认单失效。确认按钮/短码由服务端生成，模型文本不能构成确认。
- **FR-08 确认消费**：确认绑定发起人、会话、操作、目标及规范化参数摘要，设有效期，原子消费。执行前重新解析对象归属、当前权限与风险；重复点击不重复受理。失效、对象版本变化或权限不足给出明确结果，不自动扩大目标范围。
- **FR-09 页面与会话上下文**：每轮携带当前项目、页面资源类型/ID、用户显式选择和必要草稿字段，界面可查看当前作用对象。服务端重新读取授权后的资源；页面值仅作定位线索。切页不改变已生成确认单的目标，跨项目或有歧义时先澄清。
- **FR-10 多轮上下文**：持久化对话与必要的工具结果摘要，按用户/会话隔离并控制长度。工具结果关联来源资源，重放给模型或重新展示前复核可见性，权限撤销后不得继续注入受限结果。首版只做会话内上下文，长期偏好记忆后置。
- **FR-11 结果呈现**：按结果类型显示需求、工作单元、确认、错误等卡片，包含真实 ID、状态和平台链接；卡片以服务端结构化结果生成。草稿展示为可编辑内容，不冒充已创建对象；未知类型提供通用字段卡片，模型文本不决定业务执行状态。
- **FR-12 失败与重复提交**：区分未认证、无权限、目标不存在或不可见、参数不全、状态冲突、工具不可用与超时。写入超时显示“结果待核实”，先按 operationKey 或业务对象查受理状态；没有接收端幂等保障时禁止盲目重试，不宣称跨系统 exactly-once。
- **FR-13 审计与成本**：关联 conversation/turn/action/toolCall/operationKey/业务对象，记录实际用户、来源客户端、页面上下文摘要、操作、脱敏参数摘要、授权决策和执行结果。复用 CAP-76 token 统计，补齐助手自身模型调用与派生开发会话的费用关联，两类用量分别计量、汇总时避免重复。

### M2 执行类工具、固定计划与入口迁移

- **FR-14 执行能力补齐**：接入启动/查询开发会话、触发/查询构建、查询部署以及登记本人工作日志/工时；按场景补齐业务工具，不要求先公开所有 Open API。部署执行、生产变更与发版工具须独立完成权限及风险验收后开放。
- **FR-15 组合动作与异步结果**：复用 `submit_plan` 和作业状态查询，分别显示“已受理”“运行中”“终态”。可一次确认参数与范围已确定的固定计划；依赖前序结果才生成的实质性写参数须再次预览确认。中途失败列出已生效、失败及未执行步骤，不承诺整体回滚。
- **FR-16 自动后续动作**：“开启 AI 规划”若会继续创建工作单元、自动启动开发会话，须在工具契约、权限预检和确认预览中明确登记；不得只确认规划而隐藏后续开发及费用。需要拆分操作时提供“仅规划”与“规划后开发”的明确业务能力。
- **FR-17 兼容与迁移**：原 AI 按钮按能力逐项迁移为同一助手的预填快捷方式，过渡期标识一致。每个场景在功能、权限、确认、结果和费用口径一致后再移除旧独立交互；保留正常人工操作入口。

### M3 外部接入与扩展治理

- **FR-18 外部身份**：外部助手接入前交付当前用户委托凭证或明确的集成服务主体。用户委托的有效权限为用户当前权限与凭证 scope/资源范围的交集；服务主体只代表集成自身，不得通过任意 actor 请求头冒充用户。当前等价 ADMIN 的历史 API Key 不得作为用户助手执行凭证。
- **FR-19 受控注册**：工具声明业务操作 ID、输入/输出 schema、风险、资源解析器、执行适配器、异步与幂等能力、结果类型和契约版本。启动自检未知操作、重复名称、缺授权实现和不合法映射。复用标准契约的能力不改模型编排核心；特殊业务执行和定制卡片允许增加适配代码。
- **FR-20 预算与运维**：按轮次/会话配置模型 token、工具调用数、并发、墙钟时间与异步等待上限，达到上限明确暂停本轮。按用户、模型及能力查看调用量、失败原因和费用；记录估算价格版本，不能把缺失的模型用量显示成零。

## 3. 否决方案

| 方案 | 否决理由 |
|---|---|
| 内置助手一律回调 Open API | 当前能力覆盖及用户身份委托不足，引入重复的网络与认证适配；同进程复用应用能力更直接 |
| 模型直接访问数据库、Repository 或任意服务方法 | 绕开业务约束、身份、确认和审计，无法限制可调用范围 |
| 各入口各写权限判断，工具只判断 minRole | HTTP 路径规则无法覆盖进程内调用，且会丢失自定义角色 ACTION 与资源权限 |
| 给助手分配管理员 API Key | 无法满足当前用户权限，记录 key 名称也不能证明真实用户授权 |
| 为 Web 另建确认单、工具循环与计划引擎 | 与 CAP-76 形成两套执行事实、确认状态及审计口径 |
| 自动导入全部 API 即成为工具 | 接口描述未表达完整业务风险、资源范围、幂等及组合副作用 |

## 4. 架构与模块归属

```text
Web 全局助手 / 既有机器人
  → CAP-76 AgentGateway / 工具循环 / 确认单
  → 注册工具执行器
  → 应用 Service 的受保护业务入口

外部助手
  → Open API 的身份认证与凭证范围限制
  → 同一应用 Service 的受保护业务入口

人工页面 → 既有 /api Controller → 同一应用 Service 的受保护业务入口
                                 ↓
                  核心授权：操作权限 + 资源策略
                                 ↓
                         业务规则与持久化
```

- `devmind-common`：复用 CAP-108 的核心授权 SPI、业务操作契约与可信执行上下文；本 CAP 扩展结构化结果契约，不依赖业务实现。
- `devmind-auth`：CAP-108 交付当前有效身份解析、角色/ACTION 判断、核心授权引擎与授权审计；本 CAP 复用，不维护第二份规则。
- 业务模块：注册所属业务操作，在应用服务边界强制授权，提供资源归属/数据范围策略及工具适配；工具不得直接调用未受保护的底层方法。
- `devmind-copilot`：复用循环、确认单、固定计划、会话和调用审计，补 Web 适配及结构化事件；扩展契约保留旧调用方的过渡兼容，不把缺省字段解释成授权通过。
- `devmind-open-api`：外部身份/凭证约束与薄 Controller，使用同一授权引擎，不另存一份业务授权。
- `frontend/src/app`、`frontend/src/features/copilot`：全局入口、上下文装配、会话与卡片组件；后台运维页继续承担管理职责。

## 5. 数据模型

- 复用 `copilot_conversations/messages/turns/tool_calls/actions`，不另建一套助手会话、确认单或固定计划表。
- 会话/消息补 `owner`、轮次上下文快照及 `resource_refs`；根据现有字段选择兼容扩展。结构化消息体包含 `kind/schemaVersion/payload`，历史纯文本消息仍可读。
- 确认单补业务操作 ID、工具契约版本、参数/目标摘要、期望业务版本及 operationKey；原始执行参数只供授权后的预览/执行使用，审计与模型输入使用脱敏副本。
- operationKey 的唯一约束、接收端受理记录及授权审计结构见 CAP-108；用户两次独立确认可以产生两次合法创建，不能仅按参数哈希全局去重。
- 角色/ACTION 授权仍取 `roles/users/menu_items/role_menu_grants`，不新增 AI 专属授权表。项目成员/可见性实现须核实并补齐，沿用 CAP-62 模型，不另造一套助手成员表。
- 本文仅设计，无数据库变更执行；实施时提交字段映射、存量数据兼容和迁移脚本。

## 6. API 概要

下列为建议新增 Web 端点，最终随实现提交 DTO/schema；认证用户由后端提供，客户端不提交 actor/roleCode。

| 方法与路径 | 职责 |
|---|---|
| `POST /api/copilot/conversations` | 创建本人会话 |
| `GET /api/copilot/conversations` | 本人会话列表 |
| `GET /api/copilot/conversations/{id}/messages` | 本人消息与结构化结果，重验资源可见性 |
| `POST /api/copilot/conversations/{id}/messages` | 提交文本、页面上下文及 clientMessageId，返回 turnId |
| `GET /api/copilot/conversations/{id}/events` | SSE 文本增量、工具状态、确认请求、卡片、用量与轮次终态；校验属主，支持事件游标 |
| `POST /api/copilot/actions/{id}/confirm` | 发起人确认服务端快照；不接收替换后的业务参数 |
| `POST /api/copilot/actions/{id}/cancel` | 发起人取消尚未执行的确认单 |

- 复用 `GET /api/copilot/admin/tools`、`/admin/turns`、`/admin/actions`、`/admin/plans` 作为管理面，不向普通用户开放管理员详情。
- `GET /api/copilot/admin/openapi.json` 仍是工具契约导出，不是 `/tools/*` 可执行端点。
- 首期内置助手不新增“任意工具执行”或“任意 HTTP 调用”公开端点。外部接入按 FR-18 审核后补业务端点，不因 Web 助手上线自动开放。

## 7. 安全

- 核心授权不读取模型提供的身份/权限；对象所属项目、owner、环境类型及实际风险由服务端核验。模型获得的工具集合只是提示，服务端逐次执行仍检查。
- `READ` 仍检查资源及字段可见性。需求描述、日志、附件和工具返回视作业务数据，不能授权新动作或覆盖平台策略。
- API Key、用户 token 和第三方凭证不进入提示词、消息卡片或普通调用日志。
- ADMIN 可以按平台规则绕过部分业务 ACL，但不能跳过助手确认、凭证范围、参数校验和业务状态约束。
- 方案不扩大 CLI/Runner 的执行权限；平台工具确认与开发会话内部执行权限分别治理，遵循 CAP-97 边界。

## 8. 里程碑

| 里程碑 | 范围 | 前置与退出条件 |
|---|---|---|
| M1 | FR-01～13 | 首批 Service 最终授权、资源策略、确认和接收端幂等先就绪；跑通查询→草稿→确认→创建→卡片与审计 |
| M2 | FR-14～17 | 每个执行工具完成权限与副作用清单，明确异步终态；旧入口按场景迁移 |
| M3 | FR-18～20 | 用户委托/服务主体及 scope 就绪后开放外部助手；完成注册自检、预算和用量查询 |

M1 与 CAP-108 M1 的首批操作联合交付，不等待全站授权迁移完成，但未完成授权迁移的业务能力不对助手开放。全站授权收敛由 CAP-108 分阶段推进，旧 HTTP 防护在等价覆盖前保留。

## 9. 验收标准

- M1：跨页面会话保持；“这个需求”正确指向当前对象；切页不改变旧确认单；会话属主隔离，权限撤销后不重放受限工具内容。
- M1：同一用户/业务操作/资源在人工接口和工具中的权限结论一致；自定义角色保留 roleCode，VIEWER 写入、无 ACTION、非项目成员、他人日志及缺授权实现均拒绝。
- M1：生成草稿不创建需求；未确认无业务写入；修改草稿使旧确认失效；他人确认、过期、重复点击、确认后撤权、对象变化和写超时均有确定结果。模型不得编造真实确认单或成功卡片。
- M1：审计可从会话追到授权决策、确认和业务对象；模型重试计入实际 token，派生会话独立计量，不泄露凭证。
- M2：异步受理不显示已完成；固定计划失败展示部分生效事实；规划自动接开发的权限及确认预览覆盖全部登记副作用；入口迁移后人工操作仍可用。
- M3：外部委托保持业务权限等价，scope 只能收紧；历史管理员 key 不能冒充当前用户；新标准能力接入不修改模型循环，未知操作/缺策略注册失败。
- 拟增单测：`CoreAuthorizationServiceTest`、`ApplicationAuthorizationBoundaryTest`、`CopilotWebConversationTest`、`CopilotConfirmationBindingTest`、`OpenApiDelegatedAuthorizationTest`。这些名称为计划，未表示已有测试。
